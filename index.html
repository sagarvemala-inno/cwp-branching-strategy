Why one model

A CWP 2.0 release is not a single repository release

All four repositories now follow one branching strategy, one nomenclature and one release process. Consistency across the four makes release coordination, customer patching and customer migrations significantly simpler.

Release coordination

The same branch exists under the same name at the same point in the cycle in every repository. Cutting a release is one coordinated action across all four.

Customer patching

Every shipped release keeps a live branch and an exact tag. A customer running 2608 is patched from 2608, without inheriting changes they have not tested.

Customer migrations

Version history reads the same way in all four repositories. What a customer is running, and what they are moving to, stays unambiguous.

Nomenclature

Three branches, one tag, and nothing else

These four names are the whole vocabulary of the model, and each one carries the same colour on every diagram in this document. Three of them are branches and one is a tag, which is a distinction worth keeping: a branch moves, a tag does not.

The three branch roles must stay distinct. A development branch never takes release-only fixes, and a release branch never takes features.

Short-lived working branches sit outside these four. feature/* before a cut and hotfix/* after a release has shipped both exist to be reviewed, merged and then deleted, so neither is a standing role in the model.

master

Permanent. The record of what has shipped. Never developed on directly. It receives one merge per release and hands out one branch per release.

dev/<release>

Where a single release is built. Created fresh for each release. Feature-frozen at the cut, kept open for stabilisation fixes, and retired when that release ships.

release/<release>

Frozen at creation. Only stabilisation fixes land here. Remains available after shipping so customers running that release can be patched.

v<release>

A tag, not a branch. It points at the exact commit that was deployed. Every customer issue is reproduced against it.

The release cycle

One loop, repeated every release

Development happens on one branch per release. That branch is cut into a release branch, stabilised, tagged and merged back into master. The next development branch opens at the cut, so no repository is ever left without one.

The procedure

  1. Cut the release branchCreate a fresh release branch from the current development branch. This is the branch that will be deployed. The cut is the code freeze.
  2. Open the next development branch at the same commitCreated from the same commit as the release branch, so sprint work continues without interruption from the day of the cut.
  3. Stabilise through the frozen development branchdev/<release> is feature-frozen at the cut and takes stabilisation fixes only. Each fix is tested there and then merged into the release branch. It retires when the release ships.
  4. Tag the releaseTag against the exact commit that is deployed, not a branch head that may have moved since.
  5. Merge the release branch back into masterPerformed by DevOps, once the release is tagged and deployed.
  6. Merge master into the development branchThe development branch now carries every stabilisation fix from the release it succeeded. All new development for the next release happens here.

Sprints and the freeze

What the freeze stops, and what it does not

Sprint boundaries and release boundaries do not line up, and they are not required to. The cut freezes the branch being shipped. The development branch carries on from the same commit, so sprint work is never blocked.

In return, the development branch must stay release-ready at all times. The release branch inherits whatever the development branch contains at the instant of the cut, and there is no review step in between. Two rules apply:

  • Unfinished work stays on its feature branch and merges into dev/ only when it is shippable.
  • Work that must merge early goes behind a feature flag that is off by default, so it ships inert.

Stabilisation

Where a fix is authored changes at the ship

The release branch is cut five to six days before the release date. In that window it has no test coverage of its own, so a fix written straight onto it ships without ever having been exercised. That is the risk the freeze was meant to remove, not create.

So while the release is hardening, the fix is authored on dev/2608, tested there on DEV and QA, and only then merged into release/2608. dev/2608 is feature-frozen from the cut and takes stabilisation fixes and nothing else, which is what keeps that merge clean: the only difference between the two branches is the fixes themselves.

Once 2608 has shipped, dev/2608 is retired and the release branch is the only place the fix can be made. A customer hotpatch is authored on release/2608 and forward-ported into the active development branch, so the direction reverses. A fix must not be lost because it was made against an older release.

Customer hotpatches

Patch a customer without shipping them a sprint

The release branch remains available for customers running that release. A hotpatch for 2608 is developed and released from release/2608, which allows us to patch a customer without pulling in unrelated changes from the next release.

The hotpatch must then be forward-ported to the appropriate active development and release branches where the fix is required. Depending on the changes and branch divergence, this may be through merge, cherry-pick or a controlled forward-port. A fix must not be lost simply because it was made against an older customer release.

Where the fix is authored

dev/2608 was retired when 2608 shipped, so the question of which branch to write the fix on comes up again. The answer is not to revive it. A retired branch has to be kept in step with every hotpatch that lands on release/2608, and the moment it drifts you are testing against a baseline the customer is not running. Reaching for the current development branch is worse: the fix is validated against 2608.1 or 2609 code, passes there, and fails at the customer.

The rule is the same as it was before the ship. A fix is never authored on a branch that ships. So a short-lived branch is cut from release/2608 itself. That gives the correct baseline, including any earlier hotpatches, somewhere to test, and a pull request that can be reviewed.

  1. Cut hotfix/<release>.<n> from the release branchFrom release/2608 itself, never from a development branch. The branch is short-lived and is deleted once it has merged.
  2. Fix and validateAfter the ship, the only environment still running 2608 is the affected customer’s Non-Prod. That is where a hotpatch is validated, and it is what that environment is for.
  3. Raise a pull request into release/2608The release branch receives reviewed, tested merges and nothing else, exactly as it did while the release was hardening.
  4. Tag the merge commit, then forward-portDeploy that tag to the customer, and forward-port the fix into the active development branch so it is not lost in the next release.

What committing straight to the release branch costs

  • No review gate. A direct commit bypasses the pull request, so the code that goes straight to a customer gets the least scrutiny of anything in the estate.
  • The tag stops being trustworthy. Commit, test, commit again, and the branch head has moved. Which commit did the customer actually receive?
  • Concurrent hotpatches collide. Two customers, two urgent fixes, both committing directly, and the branch now holds a combination neither engineer validated.
  • No clean undo. A bad fix has dirtied a branch other customers are also patched from. Abandoning a hotfix branch is easy; reverting a shared release branch is not.
  • The build may never run. Pipelines usually build on development-branch pushes and on tags, not on release-branch commits.

Overlapping releases

Two releases in flight, one branch taking new work

Take a concrete month. On Monday 1 September, planning commits to two releases on the same day: 2608.1 shipping on 19 September and 2609 shipping on 30 September. Both are now dated and scoped, and the question every developer asks that afternoon is which branch their work goes to.

Deciding two releases on one day does not open two development branches on that day. On 1 September only dev/2608.1 exists. Work scoped to 2608.1 merges into it. Work scoped to 2609 stays on its feature branch and waits, which is precisely the discipline Figure 2 asks for and the reason it earns its place.

dev/2609 opens on 15 September, at the 2608.1 cut, from the same commit as release/2608.1. The waiting feature branches merge into it that day. From then until its own cut on 24 September it is the only branch taking new work, while release/2608.1 hardens and ships behind it.

Development branches take turns. Release branches accumulate.

These are the two halves of the answer and they behave in opposite ways.

Only one development branch takes new work at a time. dev/2608.1 until 15 September, dev/2609 until 24 September, dev/2610 after that. Each is feature-frozen at its own cut, stays open for stabilisation fixes, and retires when its release ships. There is never a moment where a developer has to choose between two open development branches.

Release branches never close. release/2608.1 does not end when 2608.1 ships on 19 September, because a customer running 2608.1 has to be patchable from it. When release/2609 is cut on 24 September there are two live release branches, and a third arrives with 2610. That number only grows, which is what Proposal 02 further down exists to bound.

DevOps creates each branch in all four repositories together, at the point of that cut. The merge rule is unchanged: master is merged into the open development branch once the release ahead of it has been tagged and merged back.

Environments

Deployment map

Where each branch is deployed

The environment model runs DEV to QA to PERFORMANCE to UAT internally, then Customer Non-Prod to Customer Production. Each stage is fed by a specific branch, and each promotion is a decision with a named owner rather than a request.

CWP 2.0 is not yet multi-tenant, so ECC, HANA and Maximo variants exist within each environment type. They are approved variants of one standard model, not purpose-built environments, and the footprint should reduce as multi-tenancy lands.

Environment discipline

No new environment by default

The model only stays lightweight if the estate stops growing. Two rules carry that, and both have a named consequence rather than an intention.

No environment per feature, customer or test scenario

Any genuine exception is explicitly reviewed and approved before creation. SaaSOps will not provision or support an exception environment without that approval.

A broken DEV is restored within one hour

Some instability is expected while multiple teams work against a common codebase. If the change cannot be fixed inside that window, revert it and restore stability.

Proposed additions

The three items below are not part of the issued standard. They close gaps that the branching model and the environment model both leave open, and each one needs a decision before it becomes policy.

Proposal 01 Deployment cadence

A published schedule instead of on-demand refreshes

Ad-hoc refreshes are the largest single source of DevOps interruption, and they are why DEV is unstable at unpredictable times rather than at known ones. The environment model already accepts that some instability is expected on DEV and asks the owning team to restore it within an hour. A fixed cadence makes that window predictable.

The proposal

  • DEV deploys three times a day on a published schedule, morning, afternoon and evening, across dev-cwp-ecc, dev-cwp-hana and dev-cwp-maximo. Work that misses a slot waits for the next one.
  • Off-schedule deploys become an exception with a named approver, not a message in a channel.
  • QA and PERFORMANCE do not deploy on request at all. Release Management decides when a release branch build is promoted into them.
  • UAT changes release over release, as the environment model already states.
  • Demo environments are not refreshed on demand. Product or PS take the call, and the environment carries a named owner.

Three slots a day is a starting position rather than a fixed number. The point is that the number is published and the same in every repository.

Proposal 02 Support window

How far back we keep patching

Every shipped release keeps a live branch, and the standard does not say when that obligation ends. Without a stated limit the set of branches that can receive a hotpatch grows with every release, and each fix has to be forward-ported through every branch between the one it was made on and the current development branch.

The proposal

A rolling support window. The current release and the two before it stay patchable from their own release branch. Anything older is out of support: a customer on it is moved forward rather than patched. On a monthly cadence that is roughly a quarter of cover.

Proposal 03 Release metadata

Every environment states what it is running

Most environment triage starts with working out what is actually deployed, and that question is usually answered by asking someone. A visible release stamp turns it into a glance, and it makes the tag the single source of truth, which is what the branching standard already depends on.

The proposal

Every environment, production included, exposes the same five fields. Where the environment allows it the stamp is visible without signing in; where it does not, it sits in the product's About panel.

Ownership

DevOps owns the mechanics. Engineering owns the code.

Ownership of the branching and release process is centralised with the DevOps team to ensure consistency across all four repositories. Engineering remains accountable for code quality and release readiness.

DevOps: consistency and execution

  • Branch creation
  • Release tagging
  • Merge-back to master
  • Creation of the next development branch
  • Release branch lifecycle and process consistency

Engineering: quality and readiness

  • Code quality
  • Release readiness
  • What is fit to merge into the development branch
  • Whether a change is a stabilisation fix or a feature
  • Forward-porting the fixes they author
